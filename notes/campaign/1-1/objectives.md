# 1-1 objective selection and `TouchAllObelisks`

## Result

`TouchAllObelisks` is an eligible **Standard medal objective**, not a required
1-1 completion objective. The 1-1 assets make the objective meaningful by
placing three one-use loot obelisks and linking the objective Lua chunk, but
they do not select it. Selection is a separate session-authority decision. In
build 103 the gameplay client learns the selected objective set from GMS
`ObjectivesInit` (`0xb7`) or `ObjectiveAdd` (`0xca`); merely registering the Lua
definition, initializing its counters, or touching an obelisk does not put it
in the five-row Objectives Log.

The retail selection policy itself remains unrecovered. In particular, there
is no retained retail 1-1 packet capture proving that `TouchAllObelisks` was
selected for a given run. For local playability, the current campaign
reconstruction deterministically selects this one evidenced optional objective
and records that server-authority fallback in `notes/help.md`. It initializes
the packaged runtime, sends `0xb7` followed by the owning player's initial
`0xb8`, and publishes coherent token snapshots after accepted touches. It does
not claim that retail always selected this objective or fabricate four other
rows merely to fill the five-row popup.

This corrects a tempting but invalid inference from the tutorial objective
initializer. The five-record `0xb7` sequence documented in
[`objectives-log.md`](objectives-log.md) is generated by the repository's
tutorial path and includes `TouchAllObelisks` in slot 2. It proves the client
wire/UI contract, but it is not evidence that retail 1-1 always chose that
same five-objective set.

## Evidence and confidence

- **Packaged content:** runtime `content.db`, Lua chunk 5
  (`lua/0x409C9F2B.lua`), its retained disassembly under
  `bin/game/logs/objectives-log`, the 1-1 `level_script` rows, and the
  `LevelObjectives` resources.
- **Build-103 native:** canonical
  `bin/game/GameBin/Game.c` and the IDA diagnostics under
  `bin/game/logs/objectives-log`.
- **Current reconstruction:** campaign and tutorial objective/session code and
  tests. Current behavior is called out explicitly and is not presented as
  retail behavior.
- **Inference:** the two trailing booleans on the final Lua token write are a
  publish/notification boundary of some kind. Their exact simulator-side
  mapping to the `0xb8` voiceover/show fields is not yet proven.

## Registration is not selection

The 1-1 `level_script` projection has 15 rows. Three distinct level events
(`6062`, `6068`, and `6069`) link callback `InteractWithObelisk` to both chunk
5 (the objective) and chunk 736 (the interaction ability). Two other event
groups link the health-obelisk objective/ability. Thus 1-1 loads the obelisk
objective code because its placed objects need the callback; the link does not
say that the objective occupies a UI slot.

Chunk 5 has identity:

| Field | Value |
| --- | --- |
| Lua chunk | `5` |
| server-data resource | `13523` |
| source identity | `lua/0x409C9F2B.lua` |
| decoded size | `2,356` bytes |
| SHA-256 | `e168a19cf64bddaff0b483b7d1b2546011d14cc4a72b5528331105c4b2133047` |
| registered name / ID | `TouchAllObelisks` / `0x61c07561` |

Its top-level bytecode ordering is exact:

1. PC 0-2 requires `Lua!GlobalDefinitions.lua`.
2. PC 3-50 creates `nObjective_Obelisks` and fills its metadata: description,
   progress and error localization GUIDs; handled event `TouchedObelisk`;
   progress/completion voiceover `vo_ship_obelisk_accessed`;
   `groupObjective=true`; `timeObjectiveRequires=true`; and medal thresholds
   3/2/1.
3. PC 51-55 calls
   `nObjective.RegisterObjective("TouchAllObelisks", nObjective_Obelisks)`.
4. Only afterward, PC 56-74 installs `Init`, `HandleEvent`, and
   `ObjectiveStatus` in `nObjectiveFns`.

The registry therefore retains a reference to a definition that is completed
by later table mutation. None of these instructions chooses a level slot or
sends a packet.

The DBPF type `0x68232164` resource at instance `0x2ea8fb98` includes
`TouchAllObelisks`, `DefeatAllMonsters`, four other objective names, and nine
level-affix choices. It is an eligibility pool, not a per-1-1 assignment.
The 1-1 level binds no tutorial-specific `LevelObjectives` record and has no
objective completion/exit callback. This is why the presence of the Lua chunk
and three obelisks cannot establish selection.

## Optional/medal semantics

The objective is optional with respect to finishing 1-1 and is best described
as a Standard medal challenge:

- `ObjectiveStatus` returns Gold for 3 touches, Silver for 2, Bronze for 1,
  and Failed for 0.
- It has no Lua success action, mission-completion gate, exit unlock, reward
  grant, or persistence write.
- `groupObjective=true` and `timeObjectiveRequires=true` are authored selector
  metadata. Neither flag means “required mission objective.”
- When selected into slot 2 by the known five-row tutorial initializer, the
  build-103 popup displays it under Standard. Slot 4, not slot 2, is the Hidden
  Bonus position.

“Medal-only” should not be read as “client cosmetic only”: progress is
authoritative simulator state and the eventual result is a medal. It means
that failing it does not fail the planet.

## Exact initialization ordering

Selection and initialization are separate operations. The Lua `Init` closure
(prototype 0.1) executes this sequence:

1. Call the private-table closure (prototype 0.0).
2. If the thread has no private table, create it and evaluate
   `GetNumInteractableObjects(SPID("InteractWithObelisk"))`; store the result
   as `totalObelisks`.
3. Write token index 1 for `kAllPlayers` to `totalObelisks` with flags
   `(false,false)`.
4. Write token index 2 for `kAllPlayers` to `totalObelisks` with flags
   `(false,false)`.
5. Do not write token 0; its zero value is the initial touched count.

One selected 1-1 obelisk marker-set variant contains exactly three loot
obelisks and two health obelisks. Only `InteractWithObelisk` is counted, so the
initialized token triplet is `(0,3,3)`. The three alternative marker sets are
equal-weight alternatives; counting all 15 authored alternatives would
incorrectly initialize the objective to 9 loot obelisks.

The build-103 client does not run this initializer merely because it receives
`0xb7`. The authoritative simulator runs objective Lua and serializes the
result. On the receiving client, `sub_537AA0` (`0x00537AA0`) clears the local
objective vector and expands every 56-byte wire record to a 68-byte record.
Thus, for a selected objective, initialization must be reflected in the record
sent by authority; receipt is not selection logic.

## Exact touch-event ordering

The interaction ability and the objective listener form two distinct stages.
An accepted use of one of the three `InteractWithObelisk` objects emits
`TouchedObelisk`. Chunk 5's `HandleEvent` closure (prototype 0.2) then:

1. Rejects any event other than `nObjectiveEvents.TouchedObelisk`.
2. Reads event GUID slot 0.
3. Calls `HasInteractableUsesLeft(guid)`; if false, returns without mutation.
4. Calls `IncrementNumTimesUsed(guid)` before changing objective counters.
5. Obtains the objective-private table.
6. Sets `numTouched=1` if absent, otherwise increments it by one.
7. Calls `SetObjectiveIntData(kAllPlayers, 0, numTouched, false, false)`.
8. Calls `SetObjectiveIntData(kAllPlayers, 1, totalObelisks, false, false)`.
9. Calls `SetObjectiveIntData(kAllPlayers, 2,
   totalObelisks-numTouched, true, true)`.

The one-use check and increment precede the counter mutation, so a repeated
event for the same consumed object cannot legitimately advance the medal. The
authored complete snapshots after the three unique uses are:

| Unique touch | token 0: touched | token 1: total | token 2: remaining | status if evaluated |
| ---: | ---: | ---: | ---: | --- |
| initial | 0 | 3 | 3 | Failed |
| 1 | 1 | 3 | 2 | Bronze |
| 2 | 2 | 3 | 1 | Silver |
| 3 | 3 | 3 | 0 | Gold |

`ObjectiveStatus` is a separate callback; `HandleEvent` updates data but does
not itself assign a medal byte or complete the level.

## Selection, visibility, and packet ordering

Build 103 has four relevant messages:

| Message | ID | Native receiver | Effect |
| --- | ---: | --- | --- |
| `ObjectivesInit` | `0xb7` | `sub_537AA0` | Replace the objective vector |
| `ObjectiveUpdated` | `0xb8` | `sub_536DA0` | Replace one player's state and three tokens |
| `ObjectivesComplete` | `0xb9` | `sub_536EE0` | Consume the completion/result snapshot |
| `ObjectiveAdd` | `0xca` | `sub_537BF0` | Append one 56-byte objective record |

An objective becomes selected/available to the popup when its ID enters the
client vector through `0xb7` or `0xca`. `MaxisObjectivePopup` (`0x0041D2E0`)
later reads five vector rows from game-state offset `+672`; `sub_41D300`
resolves each ID to its registered Lua definition and detokenizes title and
progress. Opening the log does not request objective data.

The `0xb8` `is_notification_shown` byte controls the transient
notification/voiceover path. It does **not** control whether a selected row is
visible in the Objectives Log. Conversely, a `0xb8` cannot add an unselected
ID: `sub_536DA0` first searches the existing vector and ignores an absent ID.

The repository tutorial setup currently orders its setup messages as:

```text
GameState -> DirectorState -> QuickGame (0xaf)
          -> ObjectivesInit (0xb7) -> ObjectiveUpdated (0xb8)
          -> ObjectCreate/ObjectUpdate and later scene population
```

That immediate `0xb8` updates `FinishLevelQuickly`, not
`TouchAllObelisks`. It is useful proof that the client can receive selection
before scene objects, but it is current reconstruction ordering, not a retail
1-1 capture.

Current 1-1 campaign fallback ordering is:

```text
choose one obelisk marker-set variant
-> create the TouchAllObelisks runtime for the authenticated player slot
-> run Init to retain (0,3,3), then mark only that slot active
-> publish normal campaign setup/objects
-> publish ObjectivesInit (0xb7), then one silent initial ObjectiveUpdated (0xb8)
-> accepted loot-obelisk use runs HandleEvent
-> publish each coherent authored token write only to the active player slot
```

## `0xb8` contract and 1-1 negative result

Excluding the one-byte message ID, `ObjectiveUpdated` is exactly 23 bytes:

```text
uint32le objective_id
uint8    player_index       // 0xff means all four players
uint8    medal_or_state
uint32le voiceover_guid
uint8    is_notification_shown
uint32le token[3]
```

For `TouchAllObelisks`, the objective-ID bytes are `61 75 c0 61`; the token
triplets of interest are `(0,3,3)`, `(1,3,2)`, `(2,3,1)`, and `(3,3,0)`.
The Lua writes all-player simulator data, while the wire receiver supports
either a concrete player or `0xff`.

There is no retail-evidence-backed complete 1-1 `0xb8` byte string to record:

- no retained retail 1-1 trace selects this objective;
- the current fallback seeds only the authenticated player's medal/state byte
  to one and leaves the other three slots inactive;
- the current update publisher emits only for that active player-state slot;
- the existing tutorial publisher can emit `0xb8` for this ID, but that is a
  different mode and cannot establish retail 1-1 policy.

The final Lua write's `(true,true)` flags strongly identify it as the intended
batch/presentation boundary after tokens 0 and 1 have been filled. Native
`SetObjectiveIntData` accepts both booleans, and build-103 `0xb8` has separate
voiceover and show-notification fields, but the exact flag-to-field conversion
has not been recovered. Therefore a claim that retail sent three `0xb8`
packets per touch, or that it used a particular voiceover GUID/show byte,
would be fabrication. The most that is proven is the final coherent token
snapshot and the final-write flag ordering above.

## Remaining recovery boundary

To close selection completely, obtain a retail 1-1 authority trace or recover
the missing server/simulator selector that consumes `LevelObjectives`, then
answer:

1. which pool/slot rule chooses the three Standard objectives for 1-1;
2. whether `TouchAllObelisks` is guaranteed when three loot obelisks exist or
   merely eligible/random;
3. when selected objective `Init` runs relative to marker-set realization and
   `0xb7` serialization; and
4. how the two Lua write flags choose `0xb8` voiceover and notification
   fields.

Until then, registration, progress, selection, popup visibility, and mission
completion remain separate states. The current deterministic selection is a
documented playability fallback, not recovered retail policy.
