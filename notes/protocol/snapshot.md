# Sync Snapshot diagnostics

Sync Snapshot is an opt-in, bounded incident recorder for gameplay synchronization. It records the RakNet boundary and the client/server object states needed to reconstruct why one client diverged; it does not alter gameplay, rubber-band a player, or treat a heuristic as server authority.

## Modes and commands

Darkspinner Configuration exposes `Off`, `Manual`, and `Auto`. The persisted server keys are in `[snapshot]`: `mode`, `buffer_duration_seconds`, and `delay_seconds`. The shipped configuration, server fallback, launcher model, and Fang environment fallback all default to `Off`. `Off` retains no rolling data and clears a previously active Fang ring, `Manual` retains data for an explicit dump, and `Auto` also enables anomaly-triggered dumps.

- `/ss` reports the active mode, buffer, automatic delay, retained event count, dropped event count, suppressed trigger count, and command help.
- `/ss mode [manual|auto|off]` changes collection immediately for the running server and Fang client.
- `/ss dump` captures the current rolling window.
- `/ss delay <1-3600>` changes the session-wide automatic snapshot cooldown.
- `/ss ignore <snapshot-id>` suppresses the automatic fingerprint that created that snapshot for the current server session.

The default rolling window and automatic cooldown are both 30 seconds. Server and client rings are independently bounded to 64 MiB and five minutes. Only memory-pressure eviction inside the requested window is reported as dropped capture data; routine expiry of older history is not a loss signal. A successful automatic dump starts the global cooldown and reports the detected condition, snapshot ID, player identity, and `darkspin/bugs` ZIP location through the active game-chat target. A failed dump releases the in-progress reservation without consuming that cooldown, and a missing active Blaze recipient is logged as a notification failure instead of being treated as delivery.

## Automatic signals

Auto mode currently records four evidence-backed anomaly classes:

- at least three client NACK datagrams in two seconds;
- an outgoing object lifecycle violation, such as locomotion before movement intent or a duplicate object delete;
- two consecutive client movement reports whose displacement exceeds the elapsed-time allowance without a recent authoritative teleport;
- three consecutive local Fang samples where a published, living NPC's client root position remains more than five units from the current authoritative server position.

These are deliberately diagnostic signals, not proof of cheating or permission to mutate a player's position. `/ss ignore` stores the selected incident's exact remote/object/anomaly fingerprint rather than muting unrelated problems.

## Artifact layout

Snapshots are written beneath the active runtime's `darkspin/logs/traces/snapshots` directory: normally `bin/server/darkspin/logs/traces/snapshots` for the standalone server or `bin/darkspinner/darkspin/logs/traces/snapshots` for Darkspinner. Each directory is named from the snapshot ID and UTC creation time:

Every successful manual or automatic dump also atomically publishes a transportable ZIP beneath that runtime's `darkspin/bugs` directory. For Darkspinner this is normally `bin/darkspinner/darkspin/bugs`; for the standalone server it is normally `bin/server/darkspin/bugs`. The manual completion message includes the ZIP filename; the concise automatic notice includes the snapshot ID that prefixes its ZIP and the `darkspin/bugs` location. The archive contains one snapshot-named top-level directory with the same manifest and evidence files listed below, while the unpacked trace bundle remains available for immediate local inspection and `darkrun snapshot` reanalysis.

- `manifest.json` records the build, trigger, context, player, mode, window, server and client ring occupancy, capacity truncation, counts, dropped events, and every included file's exact byte size and SHA-256 digest.
- `raknet.jsonl` stores exact server-observed datagrams in both directions, retransmissions, delivery-ordered client application payloads, trace IDs, peer generations, datagram/message/order indexes, reliability, ordering channels, and split metadata.
- `server-state.json` stores the authoritative zone/generation/projection keyframe; session bindings; every not-yet-sent gameplay packet in exact batch and packet order with bytes, identity, hash, and critical-retention status; heroes, companions, NPCs, pickups, DNA, orbs, and retained active projectiles including independently tracked multi-shot bursts; poses, resources, targets, action revisions, NPC action ownership and start state, effective movement speed, stop distance, slow scale, stun/sleep/root/silence/fear timers and fear source, targetability, self-resurrection, navigation collision, active hero pursuits; projectile ownership, authored ability/noun, position, aim point, direction, speed, remaining flight, per-shot target identity, Frozen state, and gravity deflection; live gameplay modifiers; the controlled hero's reported position and exact authoritative motion segment, goal, velocity, simulation timestamp and revision; retained attack pose, basic-combo sequence, ability release gate, cooldown reservations, hero-selection and control-effect timers, overdrive and stealth state, follow target, and next projectile identity; all three squad members' current and maximum resources, availability, deployment and recovery gates; every catalyst slot; active ability-owned runtime and object identities including Electron Sphere, traps, summons, auras, channels, drones, pets, and Tree of Life; zone level, difficulty, chain position, clock, completion identity, co-op membership, cleared spawn groups, checkpoint and population state; accepted campaign-director trigger and named-event history; encounter stages, horde waves and gates, boss admission and beam-out state, security teleporter routing, and interactable use limits; named interaction, crystal, and equipment schedules; active enemy death animation timelines, deadlines, pending tasks, collision, fade, and deletion state; objective states and tokens; named zone timeline tasks with absolute deadlines and remaining time; and the complete NPC and drop MT19937 continuation states with draw counts and SHA-256 identities.
- `client-memory.jsonl` is Fang's exact in-memory rolling ring when the client shares the local runtime. It includes whole RakNet datagrams, reconstructed application messages, frame/thread-correlated scalar action and input changes, before/after locomotion component images, lightweight auto-mode root-position probes for objects with locomotion, and a dump-time image of every live client game-object slot, locomotion component, combat action state, pending input descriptors, and controlled-player binding.
- `client.jsonl` is the matching tail of persistent observational Fang JSONL traces and remains useful when a live client-memory response is unavailable.
- `timeline.jsonl` is a normalized replay index. It expands server datagrams into application emissions, reassembles split payloads, preserves source-line references, payload hashes, scalar state values, thread/frame timing, boundary ring metadata, full locomotion flags/goal/partial-goal/desired-stop state, and both raw and RakNet-resolved movement-target identities; joins server UTC with client monotonic time through the dump request's nanosecond boundary stamp; and associates Fang's internal client handles with RakNet object IDs through each observed movement receive/apply sequence.
- `analysis.json` records automatic transport sequence, NACK/retransmit, pending-server-output completeness, ordering, object lifecycle, byte-identical server/client delivery, client apply, dump-time client action/input state, compact authoritative session replay state, capture-completeness, missing client projectiles, dedicated client-versus-server projectile-position comparisons, and mapped three-way server-position/client-goal/client-root comparisons. Sequence discontinuities are capture or receive-gap evidence unless the window also contains an actual NACK or retransmit. When the server position aligns with the client locomotion goal but the client object root remains outside the speed- and sampling-time-adjusted allowance, the report classifies the relationship as `client_locomotion_stalled` and retains the partial goal, flags, desired-stop distance, and server/client/raw-handle target identities as evidence.
- `report.md` is the readable root-cause triage summary, including the likely cause, confidence, capture metrics, dump-time client action/input fields, authoritative motion and admission state, deterministic random stream identities, squad and catalyst resources, active ability runtimes, director and encounter history, horde/boss/security/interactable state, scheduled deadlines, cooldown context, retained death lifecycles, objective replication state, authoritative NPC boundary state, explicit client-locomotion-stall and projectile-position tables, highest-distance objects, evidence locations, and focused next checks.

The client keyframe request is executed by the game-frame hook because Game's object registry, combat action state, and controlled-player state are frame-thread-owned. Fang only reads validated object, locomotion, action, input, and player memory and emits diagnostics; it does not modify those structures, packet contents, or shipped client assets. Fang stages the client-memory dump to a temporary file, flushes it, and atomically publishes `client-memory.jsonl`, so the server never treats a partially written ring as a completed boundary capture.

Remote clients still receive full server transport and authoritative-state evidence, but `client-memory.jsonl` requires the local Fang process and server to share the trace directory. The manifest records whether that boundary capture arrived.

Scheduled callback bodies and captured Go closures are deliberately not serialized. The snapshot retains stable named timeline and action-schedule identities, due times, remaining delays, and their authoritative owner state, while exact packet bytes and the complete deterministic random streams preserve the replayable boundary without attempting to execute process memory from an artifact.

## Analysis order

Start with `report.md`, then inspect its cited `timeline.jsonl` rows and the structured findings in `analysis.json`. The automatic classification is evidence triage rather than a gameplay correction: confirm it against `raknet.jsonl`, Fang's `before_apply`, `after_apply`, and dump-boundary component images, and `server-state.json`. This preserves the chain from authoritative state, through exact ordered bytes, through client application, to the next client frame.

## Offline verification

Run `darkrun snapshot <bundle-directory>` to hash every manifest-owned file, decode the source capture, and deterministically regenerate the replay and analysis in memory. The command reports integrity, likely cause, confidence, finding counts, replay/client event counts, and per-file source or derived status.

Pass `--rewrite` to replace `timeline.jsonl`, `analysis.json`, and `report.md` and upgrade the manifest hashes. Rewriting never changes `raknet.jsonl`, `server-state.json`, `client.jsonl`, or `client-memory.jsonl`; when a bundle already contains hashes, a source mismatch blocks the rewrite rather than laundering altered evidence. Older bundles without integrity metadata remain readable and can acquire hashes during an explicit rewrite.
