# Build-103 campaign obelisk drops

This note resolves the drop policy reached by the packaged
`InteractWithObelisk` and `InteractHealthObelisk` abilities. It describes the
build-103 native selection path, not darkspin's current compatibility reward
or the beta-footage proposals in `loot.md`.

## Result

Darkspin's September 5, 2026 player-requested green-obelisk override generates four or five independent health/power capsules, scattered around the obelisk, with no resurrection substitution. Each capsule retains the roster-weighted noun selection, ordinary pickup behavior, and expiry. This overrides quantity only; the table below documents the native algorithm, not this requested policy.

| Ability | Selector | Native output in a one-player campaign | Noun selection | Confidence |
| --- | ---: | --- | --- | --- |
| `InteractWithObelisk` | `0x0c` = `Loot` (`0x08`) plus `Crystal` (`0x04`) | One equipment attempt and one crystal attempt. With the authored challenge `500`, the ordinary unmodified equipment attempt is guaranteed and the crystal attempt has a base `75%` success chance. Thus the normal result is one equipment pickup, with an independently optional crystal pickup. | Equipment is generated by the native loot tables for current difficulty and eligibility; it is not a fixed rigblock. A successful crystal attempt uses the weighted, inclusive level-bounded `crystal_definition` pool. | High for selectors, attempt count, base chances, and non-fixed nouns; Medium for treating the ordinary campaign actor as having no chance modifier. |
| `InteractHealthObelisk` | `0x02` = `Orb` | The authored challenge `100` is the base orb budget. After the difficulty-indexed native scale, every complete `100` guarantees one orb and the remainder is the percent chance of one more. At the unit scale this is exactly one pickup; the native formula, rather than beta footage, controls higher-difficulty counts. | Each accepted selection is weighted between `HealthOrb.Noun` and `manaorb.Noun` from roster-average missing health/mana, with a separately gated resurrection override. | High for the budget formula and noun identities; Medium for a particular campaign difficulty's scale until the runtime table index is captured. |

The marker challenges therefore matter, but they do not choose a named noun,
recipient, destination, or lob shape. Challenge `100` supplies the orb budget.
Challenge `500` supplies the equipment and crystal chance operands. The older
proposal of a fixed four-orb health obelisk and the fixed Electro Claws reward
are not the general build-103 policy.

## Authored callers and selectors

Runtime `content.db` is recipe `35`, source build `103`. Its level-9 marker
rows prove the concrete inputs:

- marker `2655870385` is one-use `prefab_boss_obelisk.Noun`, ability
  `InteractWithObelisk`, challenge `500`;
- markers `785296806` and `2012042454` are one-use
  `prefab_health_obelisk.Noun`, ability `InteractHealthObelisk`, challenge
  `100`.

The values are directly reproducible with:

```text
darkrun db marker get marker_id=2655870385 --config bin/darkspinner/darkspin.toml
darkrun db marker get marker_id=785296806 --config bin/darkspinner/darkspin.toml
darkrun db marker get marker_id=2012042454 --config bin/darkspinner/darkspin.toml
```

Packaged chunk `736` (`Abilities/0xDAE4DF3D.lua`) calls, at PCs `87`-`98`,
`DropStuffForObject(targetObelisk, activatingAgent,
nBit.Or(nDropTypes.Loot, nDropTypes.Crystal))`. Packaged chunk `279`
(`Abilities/0xFB748FEF.lua`) calls, at PCs `88`-`94`,
`DropStuffForObject(targetObelisk, activatingAgent, nDropTypes.Orb)`. These
operands settle both source and recipient: argument 1 is the obelisk; argument
2 is the agent that activated it, not the marker, account, or an arbitrary
party member. This is Exact bytecode evidence.

`DropStuffForObject` is registered to `sub_A035C0`. It resolves those first
two object arguments, reads the optional signed selector, and sends them to
`sub_9CE8D0`. The latter queues recipient object ID, selector, deadline, and
processing flag at combatant offsets `+92..+104`, gated independently by the
source object's `can drop loot` byte `+153`. The native wrapper supplies zero
delay and false processing flag. This is High-confidence decompiler evidence;
the existing queue description in `tutorial.md` remains correct.

`sub_9CE140` gives the selector vocabulary by direct bit tests:

- `0x02`: orb;
- `0x04`: crystal/catalyst;
- `0x08`: equipment loot;
- `0x10`: DNA;
- `1`: no branch, hence no drop.

`InteractWithObelisk` consequently selects two independent branches, not one
mutually exclusive "loot or crystal" roll. `InteractHealthObelisk` reaches
only the orb branch. Confidence: Exact.

## Counts, chances, and challenge

### Health obelisk

For bit `0x02`, `sub_9CE140` obtains the source drop amount, multiplies it by
the current difficulty-indexed scale, truncates to an integer budget, and then
loops as follows:

```text
while budget > 0:
    create one orb when randomInteger(0, 99) < budget
    budget -= 100
```

This is equivalent to one guaranteed selection per complete `100`, followed
by a remainder-percent selection. The marker's `100` challenge is therefore a
count/budget operand. It is not an event label. A unit scale yields one orb;
if a different difficulty entry scales the budget, that scaled result must be
used. Claiming a fixed four capsules for every campaign use is unsupported.
Confidence: High for the algorithm and the challenge's role; Medium for any
uncaptured difficulty-index value.

### Loot obelisk crystal branch

For bit `0x04`, the loop count is `sub_9BE3D0(1)`, proven elsewhere as the
simulator's cached player count. Each iteration calls `sub_A18600` with the
current difficulty, the source amount, the obelisk object ID, the activating
agent ID, and a sampled destination. `sub_A184E0` computes the base success
threshold as `amount * 0.15` and succeeds when an integer draw in `[0,100)` is
below it. Challenge `500` therefore gives `75`, or a base `75%` chance per
player-count attempt. Attribute `65` on the activating agent can multiply that
threshold. Confidence: Exact for the native formula and `75%` base; High for
the player-count meaning.

A success does not turn `500` into a crystal noun or crystal level. The native
converts current difficulty into its crystal level, applies a weighted level
offset, then chooses among inclusive level-bounded definitions. `content.db`
contains exactly one `crystal_level_offset` row (`+0`, weight `1`) and 192
`crystal_definition` rows. For example, the first eligible family entries are
`crystal_attackspeed.Noun`/rare/epic with weights `100/20/4`; the complete
weighted pool, not this example, is authoritative. Confidence: High.

### Loot obelisk equipment branch

For bit `0x08`, the ordinary chance operand is:

```text
cachedPlayerCount * sourceAmount * lootScalar * 0.01
```

The compiled fallback `lootScalar` is `0.25`; build-103
`LabsTuning/0x3B01D7F6.prop` overrides property `0x8c6d9f60` to float `0.45`
(the payload is the `content.db` `server_data` row at resource `13516`). For a
one-player obelisk with challenge `500`, the operand is `2.25`, which is above
every uniform float draw in `[0,1)` and therefore guarantees the ordinary
attempt. Activating-agent attribute `71` multiplies the operand; a global loot
gate and downstream eligibility/allocation can still reject creation. This is
an attempt guarantee, not a promise that an invalid or empty pool must create
an object. Confidence: High.

The equipment noun is not stored on the marker and is not selected by
challenge `500`. `sub_9CDF40`/`sub_9CD990` choose a build-103 loot rigblock and
its suffix/prefix composition from current difficulty, rarity, class/science,
and eligible weapon state. `content.db`'s `loot_rigblock`, `loot_affix`, and
`loot_tuning` projections are the relevant noun/item catalog. The packaged
ability contains no Electro Claws, Photonic Repulsor, Thermic Shard, or other
rigblock identity. Confidence: High. The tutorial's durable Electro Claws
grant remains a route-specific compatibility/video result, not the native
campaign obelisk selector.

## Placement and lob

All selected branches share the same source-position sampler and lob constants.
`sub_9CE140` first resolves the obelisk's current ground position. `sub_9CA360`
initializes a sampler centered there with an initial radius of half the source
footprint, clamped to at least `1.0`. `sub_9CBDE0` tests randomized angular
candidates, adds a random radial component up to `0.625`, snaps candidates to
the navigation surface, expands the search radius by `2.5` for at most four
rings, and falls back to the source position when it finds no valid candidate.
Each pickup consumes the next sampled destination. Confidence: High for the
constants/control flow; Medium for naming the source extent "footprint"
because `sub_9D70E0`'s field name is not recovered.

The pickup is created at the source/drop position and then launched to the
sampled ground destination. Orb, crystal, and equipment paths all call
`sub_A2EF00` with lob height `2.5` and duration `0.5s`; the existing lob
reconstruction in `tutorial.md` describes the resulting coefficients. This
native path does not use the deterministic interaction-side destination that
darkspin currently uses for its tutorial compatibility pickup. Confidence:
Exact for `2.5`/`0.5` and High for source-to-sampled-destination placement.

## Recipient and pickup ownership

The queued recipient is exactly the activating agent. The crystal and
equipment branches use that object to find chance modifiers (notably
attributes `65` and `71`). Orb weighting independently reads roster-average
health and mana need; it is not keyed only to the clicked hero's two current
values.

The examined creation calls do not copy the queued agent ID into an exclusive
pickup-owner field. They create ordinary world pickups at the obelisk and use
the agent as selection/chance context. Thus "recipient" in the queue is not
evidence that only that object may overlap or collect the result. Exact
multiplayer pickup admission remains outside this path and should not be
invented from argument 2. Confidence: High for queued-agent/context semantics;
Medium for the negative ownership conclusion because the final authoritative
collection policy lives downstream.

## Evidence boundary

The concrete native policy is the selector, attempt/budget formula, weighted
noun selection, sampler, and lob described above. Remaining uncertainties are
bounded:

- the symbolic name and per-index values of the orb difficulty-scale table;
- agent attribute modifiers present in a particular live match;
- downstream inventory/capacity failures and multiplayer collection admission;
- authoritative packet batching/order after native object creation.

None of those gaps permits replacing the native formulas with the beta-inspired
fixed four-orb table or a fixed campaign equipment noun.
