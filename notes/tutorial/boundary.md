# Tutorial boundary audit

Date: 2026-07-25

> Superseded implementation policy: tutorial now constructs a full
> `zone.Zone` during setup. The conservative sequencing below remains useful
> as an ownership inventory, but its recommendation to preserve peer-local
> tutorial authorities until the final step no longer applies.

## Scope and conclusion

This audit covers `server/tutorial_command.go`, `server/tutorial_encounter.go`, and tutorial-owned state and operations still embedded in `server/gameplay_session.go`. It is based on the current production call graph and the existing `server/zone` feature APIs; no runtime database or client asset was changed.

The tutorial has one genuinely distinct business capability: the authored Cryos route that orders the ability lesson, opening encounter, opening loot, Sage/Quadra introduction, security set, teleporter handoff, arena horde, and beam-out completion. That state already has the correct home in `server/zone/tutorial/route`, with tutorial objective selection in `server/zone/tutorial/objective`.

Most other root behavior is not tutorial-specific. Tutorial sessions do not currently join a `zone.Zone`, so `tutorialPeerRuntime`, `tutorialEncounter`, and `tutorialHorde` form a second, connection-local world model beside the shared `zone` model. The root then uses generic `zone/ability` simulations and RakNet adapters while retaining duplicate enemy health, targeting, movement, pickup, objective, companion, scheduling, and death state. The safest direction is incremental adoption of the existing feature sub-sessions (`npc.Session`, `hero.Session`, `companion.Session`, `PickupRegistry`, `OrbRegistry`, `objective.Session`, `horde.Session`, `death.Session`, and `timeline.Session`) before making tutorial construct a complete `zone.Zone`.

Do not move either root file intact into `server/zone/tutorial`. That would preserve the duplicate model and put RakNet, persistence, logging, and peer-registry concerns inside a feature package.

## What is genuinely tutorial-specific

The following policy should remain under `server/zone/tutorial` or in a thin root adapter that invokes it:

- The ordered Cryos route facts and command gates in `route.Route`.
- The semantic association between content events and route milestones: second-ability lesson, Sage marker, Quadra introduction/defeat, security-set clear, teleporter entry, horde clear, and beam out.
- Developer checkpoint normalization and the choice of route phase for a checkpoint. Checkpoint-only actors and positions are diagnostics, not reusable gameplay state.
- Selection and validation of the five Cryos objective scripts. Objective evaluation itself belongs to `zone/objective`.
- Compatibility policy used only when retail content is incomplete, such as the deterministic horde budget fallback. The fallback belongs in a tutorial content/route planner, while spawned actors and wave state still use `zone/npc` and `zone/horde`.

Everything else listed in the matrix is a generic capability with tutorial-specific data.

## Hard-coded Lua callback and content ownership audit

The runtime does load the relevant bytecode and marker links from `content.db` in `server/zone/content/contentsqlite/catalog.go`, and several feature constructors validate pinned chunk identities. Therefore these are not fabricated callback bodies. The remaining defect is hard-coded dispatch and consequence selection in the root.

Additional content debt is not callback dispatch but should be resolved during the same migration:

- Enemy groups, nouns, object IDs, positions, XP, and the Sage/security actors are literal constructors (`openingTutorialEnemyDefinitions` through `tutorialTeleporterGuardDefinitions`). Convert imported level/director records into `npc.SpawnPlan`.
- `tutorialHordeCompatibilityWaveDefinitions` intentionally invents a deterministic two-listener budget because the retail random budget is not preserved. Keep this as an explicit compatibility planner until content evidence replaces it; do not bake it into `npc.Session` or `horde.Session`.
- Obelisk, orb, opening-loot, and teleporter object records are literal definitions despite corresponding marker/script/content records being available or importable.
- Player movement speed/correction, fixed hero resource maxima, basic/Ride damage, mana-primary operands, cooldowns, alert radii, and several schedule delays are root constants. Each should become a content/config input where evidence exists; only documented compatibility fallbacks should remain tutorial policy.

## Implementation sequence

1. **Adopt generic enemy authority without changing presentation.** Build tutorial `npc.SpawnPlan` records, retain dormant/reveal grouping in a tiny tutorial sequence, and replace `tutorialEnemyState`, duplicate damage, position, shock, and lookup methods with `npc.Session`. Keep all current RakNet runs and deadlines. This removes the highest-risk split-brain state first.
2. **Adopt generic target/action state.** Register the tutorial hero and Sage companions as neutral targets; replace candidate scans and pursuit with `npc.Session` and `companion.Session`. Use `timeline.Session` keys for actor recurrence while the root still produces packets.
3. **Adopt generic pickup and objective sessions.** Register tutorial orbs/loot/obelisks in `interact` registries and replace raw objective state/runtime fields with `objective.Session`. Preserve current packet adapters.
4. **Extract neutral player ability transactions.** Move one ability branch at a time out of `tutorialAbilityCommandRuntime.handle`, beginning with Electron Sphere and Tree of Life, then Sage basic, Ride the Lightning, and the held Blitz basic. Each extraction ends at neutral damage/healing/teleport intents.
5. **Unify hero/squad/companion state and lifecycle.** Make tutorial use the same hero, companion, death, and outcome sessions as campaign. Retain tutorial route events as inputs to these generic operations.
6. **Make content drive callback dispatch.** Replace callback-name consequence branches with execution of the already loaded `MarkerProgram`/interaction program and route events derived from their emitted intents. Remove fallback objective semantics from the normal path.
7. **Move remaining encoders.** After state ownership is neutral, move direct message construction into the matching `raknet103` adapters and reduce the root to decode, peer/generation admission, scheduling, persistence/stat calls, and packet publication.
8. **Only then construct a full tutorial `zone.Zone`.** At that point the required sub-sessions already have parity, so changing setup ownership is composition rather than a behavioral rewrite. Remove `tutorialCombatPresentation` and `tutorialPeerRuntime` fields as their feature owners become authoritative; retain only route/checkpoint state and connection-local protocol runs that cannot be shared.

## Verification gates for each extraction

- Run the owning feature's invariant tests and the representative tutorial integrated path; do not create one test per private scheduled step.
- Compare accepted/rejected command behavior, object IDs, packet ordering, deadlines, damage/healing/resource results, objective updates, and rollback after schedule or persistence failure.
- Prove stale-generation callbacks cannot mutate a replaced session.
- Prove rejected movement, interaction, ability, and unlock commands make no authoritative mutation.
- Prove a killing hit is committed once, produces one death lifecycle, one objective death event, and one route transition.
- For callback migrations, record the exact `content.db` marker, callback, chunk ID/hash, emitted neutral intents, and the absence of a name-based semantic switch in the root.
