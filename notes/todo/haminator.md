## Shared evidence

- The first pickup report records a five-second RakNet worker timeout. Its goroutine snapshot pins the initiating fault to `campaignInteractionRuntime.handlePickup` at the release response's unconditional `command.Ability.Index` access. Catalyst pickup commands carry `Catalyst`, not `Ability`, so the panic unwinds while the registry mutex is still held and the action cleanup defer blocks on the same mutex.
- Later archives retain the same stack evidence because the launcher log is cumulative. Each report remains tracked separately even when one root fix closes multiple symptoms.
- The replay report records `Zone checkpoint resume found on disk`, `gameplay member reattached`, and a dungeon baseline without an NPC restoration publication before ordinary movement begins.
- The invisible enemy is object 54, authored as `TutorialSpecialOne_Intro.Noun`; it retained collision, attacks, and damage but the client had no renderable model for that variant.
- The ranged report records `SupportHealerBasic` at roughly two-second intervals despite its recovered 0.6-second cooldown and 0.45-second release, pinning the visible delay to an uncleared cast presentation rather than the authoritative cooldown.
- The boss-pad report reaches its authored source area with no remaining enemies but records no activation event; repository history confirms tutorial object 28 and the arena destination that disappeared during the gameplay refactor.
- The inert final-arena report records the movement handler holding the gameplay registry mutex while tutorial scheduling re-enters the same registry through the producer guard, timing out the RakNet peer after five seconds.
- The drain implementation created source-to-target and target-to-source effects without any ownership or removal event; the revised channel binds both effects to pooled slots for deterministic cleanup.
- The original and new hitbox reports expose the inverse failure introduced by the position-only correction: `0x8d` changes the base object transform, while build 103 targeting reads the locomotion component whose goal and partial goal are written by `0x95`. The corrected pursuit stream publishes every navigation step through `0x95` and removes the competing `0x8d` writes from redirects.
